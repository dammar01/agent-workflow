# Release procedure

One version number, one tag, one manifest. Every step below is a command that already
exists in the repo — this file only fixes their order and makes skipping one visible.

## Where the version lives

`TOOL_VERSION` in `config/settings.py:20` is the single source. Everything else derives
from it:

- `CONFIG_VERSION` — `core/workspace_paths.py:44`
- `COMPONENT_VERSIONS` — `config/settings.py:32-35`
- `state.json` `version` — `core/workflow_runtime.py:698`
- `.workflow/config.json` runtime versions — `core/workflow_runtime.py:219-248`
- documentation banners in `README.md`, `dist/config/*/AGENTS.md`,
  `dist/config/claude/CLAUDE.md`, and the skill files — rewritten by
  `tools/maintain/stamp_version.py`, whose `TARGETS` table names every anchored line
- `dist/manifest.json` — regenerated by `tools/maintain/gen_manifest.py`

Never edit a version by hand anywhere but `config/settings.py`. The stamp targets are an
explicit list precisely so that an unrelated semver in prose is not rewritten by accident.

## Cutting a release

1. **Bump.** Edit `TOOL_VERSION` in `config/settings.py`.

2. **Stamp.** Propagate it and confirm nothing was missed:

   ```
   python tools/maintain/stamp_version.py
   python tools/maintain/stamp_version.py --check
   ```

   `--check` fails when a target file is missing, not only when a banner is stale. A new
   provider bundle adds a target by existing (`tools/maintain/stamp_version.py:66`), so a provider
   declared in `config/providers.py` without its `dist/config/<name>/AGENTS.md` fails here.
   That is the check working, not a false alarm.

3. **Manifest.** Regenerate and confirm:

   ```
   python tools/maintain/gen_manifest.py
   python tools/maintain/gen_manifest.py --check
   ```

   The manifest carries a sha256 and byte count per shipped file. It is what makes an
   install verifiable after the fact — `core/bundle_integrity.py` compares against it.

4. **Release notes.** Write `prompt/v<version>/changelog.md`. One directory per version,
   the existing ones are the format. Add the row to `CHANGELOG.md`.

5. **Test.** All three, in this order:

   ```
   python tests/run.py
   python tools/e2e/e2e.py
   python tools/e2e/e2e.py --full     # spends real quota, needs a configured provider
   ```

   `--full` is the only step that exercises a real delegated call end to end. It costs
   money, and skipping it means the release was never run against a live provider — record
   that decision in the release notes rather than leaving it implied.

6. **Commit, then tag.** The tag points at the commit whose `stamp_version --check` and
   `gen_manifest --check` both passed:

   ```
   git tag -a v<version> -m "agent-workflow v<version>"
   git push origin v<version>
   ```

7. **Verify the tag reproduces.** From a clean checkout of the tag:

   ```
   python tools/maintain/stamp_version.py --check
   python tools/maintain/gen_manifest.py --check
   python tests/run.py
   ```

   All three must pass with no working-tree changes. If `gen_manifest --check` reports
   drift here, the tag shipped a manifest that does not describe its own `dist/` — retag.

## What CI already covers

`.github/workflows/ci.yml` runs steps 2, 3, and 5 (without `--full`) on every push and pull
request, on Linux and Windows. `.gitlab-ci.yml` mirrors it for GitLab, gated on merge
requests and the `main`/`dev` branches, with the same steps in the same order — its Windows
job is skipped unless `WINDOWS_RUNNER_TAG` names a runner, because an unmatched GitLab tag
queues a job forever instead of failing it.

Neither host bumps, tags, or publishes anything. A release still requires a human to decide
the number and run steps 1, 4, 6, 7. The delegated end-to-end run
(`.github/workflows/e2e-full.yml`, and the `e2e:delegated` job on GitLab) is manual on both
and covers no release step: it exists to spend quota deliberately, not on a schedule.

## Known gap

There is no reproducible-build guarantee beyond the manifest hashes: the repo has no lock
file because it has no third-party dependencies (no `requirements.txt`, no
`pyproject.toml`). Reproducibility here means "the same `dist/` bytes for the same tag",
verified by step 7 — not a pinned toolchain. The Python version is pinned only in CI.
